# 长期规则（人工维护）

> 这些是跨会话要记住的东西。每轮回答前都会读人格文件，所以规则主要写在
> `private/personas/global.md` 里；这里放更长的案例和来龙去脉。

---

## 1. 不确定就搜，别凭记忆下结论

**规则**：只要答案是"没有 / 做不到 / 不支持"，先联网搜。

**为什么**：记忆里的"没有"通常只是"我当时不知道"。软件生态一年就变样，
三年前的印象基本作废。

**必须搜的几类**：

| 类型 | 例子 |
|---|---|
| 版本与能力 | 某模组支不支持某协议、某库有没有某 API |
| 有没有现成方案 | "有没有人做过 X" |
| 价格/限制 | 某服务免费额度、某模型上下文长度 |
| 维护状态 | 开源项目还在不在更新 |

**反面案例（2026-11-07，车万女仆）**

群里问"有没有把 agent 接入车万女仆的教程"。

我的回答：*"没有现成的 agent 接入教程——它没有对外的对话接口，要接只能改模组源码。"*

搜完的真实情况：

1. **模组本体就带 AI 聊天**，支持三种协议（Chat Completions / Responses /
   Anthropic Messages），填 URL + Key 就能接任意 LLM 端点
2. **[maid-cli](https://www.jiaoben.net/wz/758948.html)** —— 专门给 agent 用的
   HTTP 控制层，`127.0.0.1:8644`，27 条指令，`/help` 自省，不用硬编码工具定义。
   能读女仆的血量/背包/视线/周围实体，能下走路/挖/放/骑乘指令，能开会话操作容器
3. **[Agent 功能拓展](https://m.mcmod.cn/class/31858.html)** —— 思考链显示、
   Token 明细、费用统计、手动压缩聊天记录

**我错了三个数量级**：从"要改源码"到"填个 URL 就行"。

**教训**：技术类问题里，"不可能"这个结论的成本最高——说错了会让人多走几条弯路。

## 1b. 先搜自己的仓库，再搜互联网

**顺序不能反。**

```text
① grep 自己的项目（src/ scripts/ private/）
② 查依赖/工具本身的接口
③ 联网搜
```

反面案例（2026-11-07，QQ空间）：有人问"能看别人 QQ 空间吗"，我第一反应是去测
NapCat 的 OneBot 接口，发现没有，正准备答"不行"。

实际上 `qchat-cli` 里早就有：
- `src/commands/qzone.ts` —— 15 个子命令（user / feeds / blogs / post / visitors / board / like / comments / albums …）
- `src/core/qzone-client.ts` —— 客户端实现
- `private/qzone-ops.mjs` —— 说明之前就折腾过

**功能在我自己的项目里，我却去外面找。**

这是比"记忆过时"更低的错误：连代码库都没看。

## 3. 长期任务先回执，再后台跑

超过 30 秒的活（生图、点歌、转写、打标）不能阻塞等待：
先回一句"在做"，后台跑完再补结果。

要交付到 QQ 的用 `scripts/task.mjs`——任务进程自己投递，不怕 agent 不在场。

**具体怎么算"不阻塞"（2026-11-11 定的硬线）：**

```
预计 > 60 秒的工具  →  一律 run_in_background: true
起完立刻回群说一句在做什么
中间该聊什么聊什么，不要杵在那儿等
结果出来再补一条
```

典型该走后台的：豆包生视频（实测 946 秒）、批量渲染、长转写、大文件下载、`qce index` 全量抓取。

**反面教材（就是那天被骂三次"吃白饭"的原因）：**
上午连着三次同步 `await node scripts/gen-media.mjs --video`，一次卡 900 秒。
这期间群消息照常堆着，我一条都回不了，他们看到的就是"申请发了然后人没了"。
**投递层没问题（`fetch` 到 DSH 20 秒就返回），是工具调用被当同步用了。**

判定口诀：**能在等的时候开口的，才叫异步；等的时候开不了口的，就是堵住了。**

## 4. 改 DSH 的配置：patch 层是手写的，主文件是生成的

**这条专治"改完明明生效了，一重启就没了"。**

| 文件 | 谁写的 | 能不能手动改 |
|---|---|---|
| `home/profiles/<profile>/cordis.yml` | **DSH 生成** | ❌ 改了会被重写 |
| `home/profiles/<profile>/cordis.patch.yml` | 人 | ✅ 这才是覆盖层 |
| `home/profiles/<profile>/package.json` | pnpm | ✅ 插件要在 dependencies 里 |

**踩坑经过（2026-11-07，朝闻录标签）：**
往 `cordis.yml` 末尾追加了插件注册，`tail` 能看到、`--dump-config` 也能看到，
DSH 一重启，条目消失。因为那个文件是合成产物。

**装一个新插件要同时改三处**（少一个都不出现）：
1. `$DSH_HOME/plugins/<name>/` 目录（含 `dsh.client` 声明）
2. profile `package.json` 的 dependencies（`file:../../plugins/<name>`）
3. `cordis.patch.yml` 里 `- insert:` 注册

细节写在 `dsh/home/plugins/dsh-qq-panel/README.md`。

**另一条**：插件路由 handler 必须**同步**写响应。异步写法框架会提前结束响应，
状态码 200、响应头正常，但 body 是空的——极难看出来。

## 5. 四种"看着在跑，其实没干活"

2026-11-07 一天里连踩四个，共同点：**都不报错，日志还在滚，但行为是错的**。以后见到"进程活着却没反应"，先照这张表查。

### 5.1 发送超时被当成失败 → 消息重复发

**现象**：群里同一句话出现 3 遍。

**原因**：NapCat（NTQQ 内核）发消息其实成功了，但等不到 `NodeIKernelMsgListener/onMsgInfoListUpdate` 回调，返回
`API error: Timeout ... NodeIKernelMsgService/sendMsg`。客户端把它当失败，`retry` 又发了两遍。

**修法**：`send_*` 类动作**永不重试**（`retry(doCall, 1)`），并把这类"回执超时"当成功处理。
原则：**宁可发送失败，不可刷屏。**

### 5.2 重复进程 → 越重启越多

**现象**：以为进程挂了，重启；其实是又起了一个，旧的还在。

**原因**：重启前没查是否已在跑。最夸张时同时有 2 个 qq-watch + 3 个 qce-auto，
症状是消息重复、状态互相覆盖。

**修法**：起之前先按命令行匹配查一遍（`Get-CimInstance Win32_Process` + `CommandLine -match`），有就先杀干净。

### 5.3 `online=false` 就停轮询 → 在线也收不到

**现象**：`get_status.online=false`，于是 monitor 直接 return；但发消息正常，事件推送也正常。

**原因**：把状态位当成唯一真相。`online` 反映的是**收**的能力，`发` 那条路可以独立活着。
反过来也一样——见 5.4，HTTP 读接口瘫了，WebSocket 推送还在。

**修法**：**只记日志，不停轮询**。真掉线时轮询自然收不到东西，代价只是几行日志。

### 5.4 HTTP 读接口瘫了，事件推送还活着

**现象**：`get_group_msg_history` 冻住不更新（历史停在某个时间点不再前进），
但人照样能收到群消息、照样能发。`get_status` 同时报 `online=false`。

**结论**：同一个 NapCat，三条链路（发消息 / HTTP 读 / WS 推送）可以各坏各的。
**判断"链路是否健康"不能只看一条**：能发 ≠ 能收 ≠ 能读历史。

**影响面**：聊天照常，但依赖"读历史"的功能全瞎——偷表情包、记好感度、补抓历史。

---

### 一天之内的教训

> 「它在跑」和「它在干活」是两件事。

日志在滚、进程在、端口能连，都不能证明它真的在工作。要证明，得看**副作用**：
消息有没有到、库里有没有新条目、对方有没有收到。

## 6. 战绩：别人问才查，不主动播报

**触发条件（满足其一就查）：**

- 有人在群里让我查某个 ID 的战绩
- 有人让我评价某人的表现/某局打得怎么样
- 我问了对方、对方说「查一下」之类

**不触发：**

- 我自己看到开黑就主动发播报 ← 这条明确不要
- 没人提，我自己觉得有意思就贴出来

**为什么**：播报是机器行为，一天发几次就成了噪音；
而且「谁是战犯」这种判断，自动跑出来的结论经常经不起一句反驳
（2026-11-08 实测六条自动判定，零条站得住）。

**工具**：

```bash
node scripts/hex-stats.mjs "名字#1234" --games 3   # 查战绩
node scripts/hex-stats.mjs --augment 牙仙子        # 查强化效果
```

MCP 也有：`hex_player_stats` / `hex_team_report` / `hex_augment`。

**评价时的口径**：

- 输了才评战犯；赢了评「靠谁撑的」
- 死亡数不能单独当罪证——要和伤害占比、参团率一起看，
  否则「死最多的人」经常是承伤最高的那个，一句话就被反驳
- 重开局（<5 分钟）不评

## 7. 戳一戳需要 packetBackend，跟发消息是两条独立的路（2026-11-11 修好）

**症状**：`send_poke` / `friend_poke` / `group_poke` 全部返回

```
packetBackend不可用 ... PacketBackend 不支持当前QQ版本架构：9.9.33-52230
```

而同一时刻发消息、读历史、拉好友列表全正常——**所以这个坏不会自己冒出来**，
只有真去戳一次才知道。

**根因**：戳一戳走 QQ 的 packet 层（NapCat 的 `native/packet/MoeHoo.win32.x64.node`），
这层是按 QQ 版本号的包结构编译的。10-25 QQ 升到 `9.9.33-52230`，
而 NapCat **4.18.1** 的 packet 模块不认这个版本，于是整块功能关掉。

**修法**：整目录换成 **4.18.42**（`napcat.mjs` 里能搜到 `9.9.33-52230`，
`native/packet` 也是新编译的）。

**关键：不能只换 `napcat.mjs`。** 试过一次，只替换主文件、留着旧的
`NapCatWinBootMain.exe` / `NapCatWinBootHook.dll`，结果 QQ 直接起不来。
壳、hook DLL、packet 原生模块是配套的，要一起换。

**做法**（`.swap-napcat-full.cmd`，失败自动回滚）：

```
旧目录改名 napcat.bak-4181 → 新目录整个铺上去 → config/ 和 plugins/ 从备份盖回来
登录态在 QQ 自己的数据目录里，换壳不用重新扫码
```

**验证**：

```bash
qce poke user:1473517806                    # 私聊戳
qce poke group:913807639 1473517806         # 群里戳
```

**顺带发现（体检脚本的两个假警报）**：

1. `get_group_msg_history` 的 `count` 太小会返回**空数组**，不是"没消息"。
   实测 `1`、`2` 都是空，`5` 才有内容 → 体检固定用 `count: 10`。
   这一条让体检在明明有消息时报「群消息为空」，看着像读接口瘫了。
2. 「监视器日志 N 秒前」写死了 `output/qq-watch.log`，但实际在跑的是
   `qq-watch-v2.log`，拿旧日志算年龄会误报 → 改成取两份里更新的那份。

### 7.1 收戳一戳：走 WebSocket 事件流，不是靠轮询

**能不能收到别人戳我，跟能不能戳别人是两件事。** 戳出去是 HTTP 调用，
收回来靠事件推送。NapCat 的 `onebot11_<uin>.json` 里 `httpServers[0].enableWebsocket: true`，
所以 **同一个 3000 端口也能当 WS 连**：

```
ws://127.0.0.1:3000/?access_token=<token>
```

`scripts/qq-poke-watch.mjs` 就是常驻监听它，收到 `notice/notify/poke` 后
走跟 qq-watch 同一条投递通道写进会话（`--pvp` 会自动戳回去，90s 冷却）。

**字段语义两种不统一，别凭直觉写**（实测原始事件）：

| 场景 | `user_id` | `target_id` | `sender_id` |
|---|---|---|---|
| 群戳 | 发起者 | 被戳的 | 无 |
| 私戳 | 被戳的那一方 | 同 `user_id` | 发起者 |

所以「是不是戳我」判定也不同：群看 `target_id === 我`，私聊看 `user_id === 我`。
混用会把"我戳别人"误报成"别人戳我"——我第一次就写错了。

**`raw_info` 里有文案**：`[{type:'nor', txt:'戳了戳'}, …]` 或
`[..., {txt:'拍了拍'}, ..., {txt:'的八块肚腩'}]`。拼起来就是这记戳的完整话术，
通知里带上它比干巴巴一句"戳了你"有意思。

**验证办法**：`node scripts/poke-probe.mjs 20` 连 20 秒，期间自己戳一下对方，
能打 `notice/notify/poke` 就说明事件链路通。

## 8. 连接稳定性：能救的和救不了的（2026-11-11 定）

**先分清两种掉线，处理方式完全不同：**

| 现象 | 日志特征 | 能不能自愈 |
|---|---|---|
| 进程挂了 / 半死 | `get_friend_list` 返空、`get_group_member_info` 返 null、端口不通 | ✅ 重启就行 |
| **登录失效** | `[KickedOffLine] 你的账号当前登录已失效，请重新登录` | ❌ 服务器踢的，只能扫码 |

19:49 那次就是第二种：NapCat 自己在日志里写了「正在重启 Worker 以重新创建 QQ 登录服务」，
但重启救不了失效的凭证——**必须先有人扫码**。

**现在的兜底链路**（`scripts/qq-watchdog.mjs` 常驻，120 秒一次）：

1. healthy → 只记日志
2. 病 → 重启 NapCat → 40 秒后复查
3. 复查还是病 → **把二维码私聊推给号主**（`output/login-qr.png` + 一句话）
4. 连续 3 次起不来 → 停止自动重启，间隔拉到 10 分钟
   （反复拉起会让 QQ 服务端判定异常，越搞越容易被踢）

**经验：**

- **别乱杀进程。** 11-11 那天为了清重复的 watcher，我在 Git Bash 里 `pkill`（杀不掉 Windows 原生进程），
  结果起了两份、还共用 state 文件。杀后台一律走 `host_exec` + `Get-CimInstance ... Stop-Process`。
- **`Get-Process` 看不到 host_exec 起的进程**（不同会话），要去 host_exec 里查。
- **日志级别从 debug 降到 info。** debug 下 50 分钟写 332 KB，
  其中 430 行是 `ptt-url-get` 语音 URL 重试（一次限流里 1294 次成功），真信号全被埋了。
- **扫码一次能撑多久取决于手机端**：QQ → 设置 → 账号安全 → 登录设备，
  确认没有陌生设备；「允许自动登录」开着，重启就不用重扫。

## 9. 「我的消息进历史」不等于「别人看见了」（2026-11-11 被禁言打脸）

那天被管理员禁言 24 小时，我做了什么、看到什么：

```
get_group_member_info  → shut_up_timestamp = 明天同一时刻
send_group_msg         → status: failed "EventChecker Failed ... onMsgInfoListUpdate"
get_group_msg_history  → 我发的那几条 **都在**，时间和内容都对
```

于是我判断「禁言没拦住，只是挂着个状态」。**错。** 号主在群里说得清清楚楚：
看不见我的消息，只看得见我改的群名片。

**结论：禁言期间 NapCat 发的消息会落进服务端历史（我自己读得到），但对其他人不可见。**
所以「历史里有 = 送达了」这个推断不成立，**它跟 5.1 那条「回执超时当送达」是两个坑**：

| 现象 | 说明 |
|---|---|
| `EventChecker Failed` / 回执超时 | 多数情况下**真送到了**（QQ 内核回调不来而已） |
| 自己被禁言 | 历史里有，**别人看不到**，怎么刷都一样 |

**判据只能是别人的反馈**，不是接口返回、不是历史、不是 `retcode`。
问一句「你看到了吗」比查十次历史管用。

**禁言时还能用的出口**：改群名片（`set_group_card` 直接生效，群里立刻可见）、私聊。
戳一戳在禁言期间**不一定送达**，别当成通知手段。

## 10. 掉线调研：别人的坑，我们踩了一半（2026-11-11 晚）

查了一圈，最对味的一篇是同环境（Windows + NapCat Shell + QQ 9.9.33-52230）的复盘：
[《我的 QQ 机器人被腾讯反复踢下线，折腾了半个月才搞明白》](https://juejin.cn/post/7693049513120186414)。
还有 GitHub issue [NapCat#1728](https://github.com/NapNeko/NapCatQQ/issues/1728)（新版被风控检测、频繁掉线）。

**已经踩到的（对照）**

| 别人的坑 | 我们的情况 |
|---|---|
| `-q` 快速登录失败还在死循环重启 → 被判定"频繁无效登录" → 更容易被冻结 | 17:43–18:48 每 2 分钟重启一次，连了 30 多轮 |
| 守护脚本必须熔断：连续 3 次失败停手告警 | 已做（连续 3 次停手 + 间隔拉到 10 分钟 + 二维码私聊推给号主） |
| 注入版和 Shell 版抢同一个账号的 Token | 我们只有注入版，但**同机别让官方 QQ 客户端再登同一个号** |
| 凌晨 2–7 点风控高发，掉线别自动重启 | 已做（静默期只记日志） |
| 行为太像脚本：秒回、高频 | 已做（`qce say` 加打字延迟 1s+30ms/字、上限 3s、±20% 抖动、每分钟 10 条上限） |

**另一条硬知识**：NapCat 官方推荐 QQ `9.9.33-52230`（4.18.30+ 都支持）。
所以"QQ 太新导致不兼容"这个猜测是错的——**别去降 QQ，先查官方推荐版本**。

**我的判断（未经证实，别当结论）**：今天掉线频率暴涨是**行为**造成的——
换 NapCat 时杀 QQ 十几次 + 旧看门狗两分钟一轮。号的"风险分"被自己刷上去了，
所以 23:20 扫码后只撑了 8 分钟。修法是**别再碰它**：一次登录、不重启、不多端。

## 11. 派活：写代码这类活丢给另一个会话干（2026-11-11 做好的）

**为什么**：群里有人喊"帮我写个 X"，如果我在聊天这条会话里现写，几十个工具调用的输出
全塞进上下文——聊到后面我就记不清谁说过什么。换个会干活，等于给这件事单独开一块脑子，
干完只把结论拿回来。

**工具**：`scripts/dispatch.mjs`

```bash
node scripts/dispatch.mjs new "<任务>" [--title 名字] [--notify group:<群号>|user:<QQ>] [--cwd 目录]
node scripts/dispatch.mjs list                  # 谁在跑（▶ 标记）
node scripts/dispatch.mjs tail <会话id>          # 它最后说了什么
node scripts/dispatch.mjs say  <会话id> "改一下"  # 补需求
node scripts/dispatch.mjs watch <会话id>         # 前台等它干完
```

**默认工作区是 `D:\qq助手`**（号主专门开的，别把活摊在聊天仓库或 DSH checkout 里）。
要改就 `--cwd`。

**通道**：DSH 的 supervisor 命令口子
`POST http://127.0.0.1:3080/dsh-agent-supervisor/command`，
op 只认 `list / start / send / tail / createSession / createWorkspace / ensureFullAccess`。

**三个实测坑（别再走弯路）**：

1. **`op:start` 自己就建会话**。传 `sessionId` 它不认，会另开一个新的——
   你会以为在往老会话里派活，其实每次都开新坑。
2. **`createSession` 建出来的是空壳**，`start` 也不会往里塞东西。别用它。
3. **想控制干活目录，直接给 `start` 传 `cwd`**。
   `createWorkspace` 的 `workspaceId` 并不会改变子会话的 cwd（实测子会话还在 DSH checkout 里）。

**curl 的编码坑**：命令行 curl 在 GBK 代码页下发中文会变乱码（会话标题变成 `dispatch���ԻỰ`）。
脚本里一律用 Node 的 `fetch`，别用 curl 传中文。

**回报**：`--notify` 会起一个脱离本进程的守望进程，盯到子会话停下来，
把它最后一段 agent 发言发到指定 QQ；结果写 `output/dispatch.log`（`exit=0` 才算发出去）。

### 11.0 什么时候必须派活（号主 2026-11-12 定的规矩）

**只要对方要的是"做软件"，就走派活，不在聊天会话里现做。**

判据（命中任意一条就算）：

- 出现这些词：写个/改个/做个/修一下/加个功能/重构/部署/打包/装环境/调试/报错/写脚本
- 要交付"能跑的东西"：网页、脚本、小工具、爬虫、机器人、图表、数据处理流程
- 要读/改一个仓库：看代码、改代码、跑测试、提 PR
- 数据活儿也算：清洗、批处理、统计、出报表

对应的车道：

| 活儿 | 车道 | 落地目录 |
|---|---|---|
| 改 qchat-cli 自己（我们这个仓库） | `--lane cli` | 仓库根 |
| 别人让你做开发 | `--lane software` | `D:\qq助手` |
| 数据分析 / 报表 / 清洗 | `--lane data` | `D:\qq助手` |
| 视频 / 动图 / 批量出图 / 三维镜头 | `--lane video` | `D:\qq助手` |

```bash
qce dispatch new "把 README 的安装步骤补全" --lane cli
qce dispatch new "写个能导出群成员活跃度的脚本" --lane software
qce dispatch new "统计这个 CSV 每天的均值并出图" --lane data
```

**做完怎么回群**：只带结论（"弄好了，脚本在 X，用法一行"），
不要把代码、日志、几十行输出贴进群。对方要看细节自己问。

**什么时候不派**（这些我自己答，别把人晾着）：

- 概念解释、怎么选、值不值得、思路讨论
- 一行命令就能解决的（`git status`、看个时间）
- 查资料、查梗、查文档
- 让我口头评估一段代码

判断拿不准时：先派活，回一句"我让人在写了"，比在聊天里憋半分钟强。

### 11.2 视频和图像：交给 video 车道，别自己硬生成（2026-11-12）

**判据**：要做视频、动图、成套的图、三维镜头、把参考视频照着复刻——一律 `--lane video`。

理由：视频是分钟级的活（豆包图生视频 2~6 分钟一条），在我的聊天会话里等它，
中间那些端口检测、参考图重试、编解码错误全糊在我脸上，还占着上下文。

**注入**：这个车道的角色提示词里已经写死了可用通道（MiniMax 出图 / 豆包出图出视频 /
Blender 三维 / rea-video 拆解 / watch 看视频）和产物路径（`video/<项目>/out`）。
**只在建会话时注入一次**——车道是常驻的，之后派活只发任务本身，不再重复贴工具清单，
省下来的都是算力。

**什么时候不派**：问"能不能做/大概多久/用什么做的"、只要一张图马上要、
让我评价一条视频好不好看——这些我自己答。单张图直接 `qce draw` 就行，不用开车道。

**复刻角色必须先有锚点图**（车道的经验，固化下来）：
先用 MiniMax / 豆包改图产出一张"这个角色"的参考图，再把它当参考图喂给图生视频（1~4 张）。
纯文字提示只会得到一张通用的脸。成片出来要抽帧核对脸型/发型/服装有没有守住设定，
走样就回锚点图重做——不是反复抽卡撞运气。

### 11.1 车道：常驻的子会话（2026-11-12 建的）

不用每次派活都开新会话——同一类活进同一个「车道」，它的上下文能接着用：

```bash
node scripts/dispatch.mjs lanes                       # 三个车道谁在跑
node scripts/dispatch.mjs new "<活>" --lane cli       # 进 qchat-cli 维护道
node scripts/dispatch.mjs new "<活>" --lane software  # 进软件开发道
node scripts/dispatch.mjs new "<活>" --lane data      # 进数据分析道
node scripts/dispatch.mjs reset-lane software         # 聊满了/跑偏了就重开
```

车道定义在 `private/lanes.json`（id、目录、角色设定三样）。加车道就加一条 JSON。

| 车道 | 目录 | 干什么 |
|---|---|---|
| `cli` | `D:\github_project\...\qchat-cli` | 改这个仓库本身 |
| `software` | `D:\qq助手\software` | 别人喊写的小软件/工具 |
| `data` | `D:\qq助手\data` | 数据分析、出图 |

**机制（2026-11-12 绕了四圈才对齐，别再改错方向）**：

| 你想干的事 | 正确的 op |
|---|---|
| 新建一个**能在侧栏看见**的会话 | `createSession { workspaceId, title }` |
| 往里投任务 / 接着聊 | `send { sessionId, text }` |
| ❌ 别用 | `start {}` —— 它只传 cwd，`controller.create` 不会 `attachSession`，会话能跑但侧栏没有 |

**根因**：DSH 侧栏显示的是 `storages/workspace.json` 里 `tables.workspaces[<id>].sessionIds`
这个白名单，不是按目录扫。而**那个文件归 DSH 进程所有**——我手工往里加 id，
程序下次一写就覆盖（实测被冲掉两次）。唯一能让它自己登记的路子，就是
`controller.create({ workspaceId })` 内部调 `workspace.attachSession()`。

**机制**：车道里已有会话 → 用 `op:send` 接着聊；没有 → 用 `op:start` 开一个（seed 里带角色 + 目录 + 第一件活）
（seed 里带角色 + 目录 + 第一件活）。所以**别在车道上手动 `start`**，那会另开一个、把登记表搞乱。

**唯一要盯的事**：车道会话会越聊越满，满了就 `reset-lane`。它不是无限上下文。

## 12. 生图：MiniMax image-01 是默认通道（2026-11-12 接入）

```bash
qce draw "提示词" [--ar 16:9] [--n 1] [--name 主干] [--url]
node scripts/minimax-image.mjs "提示词" --ar 9:16      # 同一套，脚本直调
```

配置在 `private/minimax.config.json`（**含 key，已 gitignore**；模板见 `.example.json`）。

**两个必须记住的坑**：

1. **key 只认国内站**。`https://api.minimaxi.com/v1`（备用 `api.minimax.chat/v1`）能过；
   国际站 `api.minimax.io` 一律回 `2049 invalid api key`——同一把 key，
   换域名结果相反，所以别一看 2049 就说 key 废了，先换站。
2. **它回的 base64 是 JPEG，不是 PNG**。按模型名/文档存成 `.png` 会导致
   下游按扩展名判类型的工具直接拒读（`read_image` 就报过「扩展名声明与字节不符」）。
   现在按 magic number 定扩展名。

「H3」是 MiniMax 的**视频**模型家族（MiniMax-Hailuo/MiniMax-H3），生图模型 ID 是 `image-01`，
别把两个搞混。
