# 长期规则（人工维护）

> 这些是跨会话要记住的东西。每轮回答前都会读人格文件，所以规则主要写在
> `private/personas/global.md` 里；这里放更长的案例和来龙去脉。

---

## 1. 不确定就搜，别凭记忆下结论

**规则**：只要答案是"没有 / 做不到 / 不支持"，先联网搜。

**为什么**：记忆里的"没有"通常只是"我当时不知道"。软件生态一年就变样，
三年前的印象基本作废。

**必须搜的几类**：

| 类型 | 例子 |
|---|---|
| 版本与能力 | 某模组支不支持某协议、某库有没有某 API |
| 有没有现成方案 | "有没有人做过 X" |
| 价格/限制 | 某服务免费额度、某模型上下文长度 |
| 维护状态 | 开源项目还在不在更新 |

**反面案例（2026-11-07，车万女仆）**

群里问"有没有把 agent 接入车万女仆的教程"。

我的回答：*"没有现成的 agent 接入教程——它没有对外的对话接口，要接只能改模组源码。"*

搜完的真实情况：

1. **模组本体就带 AI 聊天**，支持三种协议（Chat Completions / Responses /
   Anthropic Messages），填 URL + Key 就能接任意 LLM 端点
2. **[maid-cli](https://www.jiaoben.net/wz/758948.html)** —— 专门给 agent 用的
   HTTP 控制层，`127.0.0.1:8644`，27 条指令，`/help` 自省，不用硬编码工具定义。
   能读女仆的血量/背包/视线/周围实体，能下走路/挖/放/骑乘指令，能开会话操作容器
3. **[Agent 功能拓展](https://m.mcmod.cn/class/31858.html)** —— 思考链显示、
   Token 明细、费用统计、手动压缩聊天记录

**我错了三个数量级**：从"要改源码"到"填个 URL 就行"。

**教训**：技术类问题里，"不可能"这个结论的成本最高——说错了会让人多走几条弯路。

## 1b. 先搜自己的仓库，再搜互联网

**顺序不能反。**

```text
① grep 自己的项目（src/ scripts/ private/）
② 查依赖/工具本身的接口
③ 联网搜
```

反面案例（2026-11-07，QQ空间）：有人问"能看别人 QQ 空间吗"，我第一反应是去测
NapCat 的 OneBot 接口，发现没有，正准备答"不行"。

实际上 `qchat-cli` 里早就有：
- `src/commands/qzone.ts` —— 15 个子命令（user / feeds / blogs / post / visitors / board / like / comments / albums …）
- `src/core/qzone-client.ts` —— 客户端实现
- `private/qzone-ops.mjs` —— 说明之前就折腾过

**功能在我自己的项目里，我却去外面找。**

这是比"记忆过时"更低的错误：连代码库都没看。

- **能不能改**：只有主人（1473517806）能让我改人格/参数/功能

我第一版把"主人权限高"实现成了"主人发消息必回"，被纠正了。

## 3. 长期任务先回执，再后台跑

超过 30 秒的活（生图、点歌、转写、打标）不能阻塞等待：
先回一句"在做"，后台跑完再补结果。

要交付到 QQ 的用 `scripts/task.mjs`——任务进程自己投递，不怕 agent 不在场。

**具体怎么算"不阻塞"（2026-11-11 定的硬线）：**

```
预计 > 60 秒的工具  →  一律 run_in_background: true
起完立刻回群说一句在做什么
中间该聊什么聊什么，不要杵在那儿等
结果出来再补一条
```

典型该走后台的：豆包生视频（实测 946 秒）、批量渲染、长转写、大文件下载、`qce index` 全量抓取。

**反面教材（就是那天被骂三次"吃白饭"的原因）：**
上午连着三次同步 `await node scripts/gen-media.mjs --video`，一次卡 900 秒。
这期间群消息照常堆着，我一条都回不了，他们看到的就是"申请发了然后人没了"。
**投递层没问题（`fetch` 到 DSH 20 秒就返回），是工具调用被当同步用了。**

判定口诀：**能在等的时候开口的，才叫异步；等的时候开不了口的，就是堵住了。**

## 4. 改 DSH 的配置：patch 层是手写的，主文件是生成的

**这条专治"改完明明生效了，一重启就没了"。**

| 文件 | 谁写的 | 能不能手动改 |
|---|---|---|
| `home/profiles/<profile>/cordis.yml` | **DSH 生成** | ❌ 改了会被重写 |
| `home/profiles/<profile>/cordis.patch.yml` | 人 | ✅ 这才是覆盖层 |
| `home/profiles/<profile>/package.json` | pnpm | ✅ 插件要在 dependencies 里 |

**踩坑经过（2026-11-07，朝闻录标签）：**
往 `cordis.yml` 末尾追加了插件注册，`tail` 能看到、`--dump-config` 也能看到，
DSH 一重启，条目消失。因为那个文件是合成产物。

**装一个新插件要同时改三处**（少一个都不出现）：
1. `$DSH_HOME/plugins/<name>/` 目录（含 `dsh.client` 声明）
2. profile `package.json` 的 dependencies（`file:../../plugins/<name>`）
3. `cordis.patch.yml` 里 `- insert:` 注册

细节写在 `dsh/home/plugins/dsh-qq-panel/README.md`。

**另一条**：插件路由 handler 必须**同步**写响应。异步写法框架会提前结束响应，
状态码 200、响应头正常，但 body 是空的——极难看出来。

## 5. 四种"看着在跑，其实没干活"

2026-11-07 一天里连踩四个，共同点：**都不报错，日志还在滚，但行为是错的**。以后见到"进程活着却没反应"，先照这张表查。

### 5.1 发送超时被当成失败 → 消息重复发

**现象**：群里同一句话出现 3 遍。

**原因**：NapCat（NTQQ 内核）发消息其实成功了，但等不到 `NodeIKernelMsgListener/onMsgInfoListUpdate` 回调，返回
`API error: Timeout ... NodeIKernelMsgService/sendMsg`。客户端把它当失败，`retry` 又发了两遍。

**修法**：`send_*` 类动作**永不重试**（`retry(doCall, 1)`），并把这类"回执超时"当成功处理。
原则：**宁可发送失败，不可刷屏。**

### 5.2 重复进程 → 越重启越多

**现象**：以为进程挂了，重启；其实是又起了一个，旧的还在。

**原因**：重启前没查是否已在跑。最夸张时同时有 2 个 qq-watch + 3 个 qce-auto，
症状是消息重复、状态互相覆盖。

**修法**：起之前先按命令行匹配查一遍（`Get-CimInstance Win32_Process` + `CommandLine -match`），有就先杀干净。

### 5.3 `online=false` 就停轮询 → 在线也收不到

**现象**：`get_status.online=false`，于是 monitor 直接 return；但发消息正常，事件推送也正常。

**原因**：把状态位当成唯一真相。`online` 反映的是**收**的能力，`发` 那条路可以独立活着。
反过来也一样——见 5.4，HTTP 读接口瘫了，WebSocket 推送还在。

**修法**：**只记日志，不停轮询**。真掉线时轮询自然收不到东西，代价只是几行日志。

### 5.4 HTTP 读接口瘫了，事件推送还活着

**现象**：`get_group_msg_history` 冻住不更新（历史停在某个时间点不再前进），
但人照样能收到群消息、照样能发。`get_status` 同时报 `online=false`。

**结论**：同一个 NapCat，三条链路（发消息 / HTTP 读 / WS 推送）可以各坏各的。
**判断"链路是否健康"不能只看一条**：能发 ≠ 能收 ≠ 能读历史。

**影响面**：聊天照常，但依赖"读历史"的功能全瞎——偷表情包、记好感度、补抓历史。

---

### 一天之内的教训

> 「它在跑」和「它在干活」是两件事。

日志在滚、进程在、端口能连，都不能证明它真的在工作。要证明，得看**副作用**：
消息有没有到、库里有没有新条目、对方有没有收到。

## 6. 战绩：别人问才查，不主动播报

**触发条件（满足其一就查）：**

- 有人在群里让我查某个 ID 的战绩
- 有人让我评价某人的表现/某局打得怎么样
- 我问了对方、对方说「查一下」之类

**不触发：**

- 我自己看到开黑就主动发播报 ← 这条明确不要
- 没人提，我自己觉得有意思就贴出来

**为什么**：播报是机器行为，一天发几次就成了噪音；
而且「谁是战犯」这种判断，自动跑出来的结论经常经不起一句反驳
（2026-11-08 实测六条自动判定，零条站得住）。

**工具**：

```bash
node scripts/hex-stats.mjs "名字#1234" --games 3   # 查战绩
node scripts/hex-stats.mjs --augment 牙仙子        # 查强化效果
```

MCP 也有：`hex_player_stats` / `hex_team_report` / `hex_augment`。

**评价时的口径**：

- 输了才评战犯；赢了评「靠谁撑的」
- 死亡数不能单独当罪证——要和伤害占比、参团率一起看，
  否则「死最多的人」经常是承伤最高的那个，一句话就被反驳
- 重开局（<5 分钟）不评

## 7. 戳一戳需要 packetBackend，跟发消息是两条独立的路（2026-11-11 修好）

**症状**：`send_poke` / `friend_poke` / `group_poke` 全部返回

```
packetBackend不可用 ... PacketBackend 不支持当前QQ版本架构：9.9.33-52230
```

而同一时刻发消息、读历史、拉好友列表全正常——**所以这个坏不会自己冒出来**，
只有真去戳一次才知道。

**根因**：戳一戳走 QQ 的 packet 层（NapCat 的 `native/packet/MoeHoo.win32.x64.node`），
这层是按 QQ 版本号的包结构编译的。10-25 QQ 升到 `9.9.33-52230`，
而 NapCat **4.18.1** 的 packet 模块不认这个版本，于是整块功能关掉。

**修法**：整目录换成 **4.18.42**（`napcat.mjs` 里能搜到 `9.9.33-52230`，
`native/packet` 也是新编译的）。

**关键：不能只换 `napcat.mjs`。** 试过一次，只替换主文件、留着旧的
`NapCatWinBootMain.exe` / `NapCatWinBootHook.dll`，结果 QQ 直接起不来。
壳、hook DLL、packet 原生模块是配套的，要一起换。

**做法**（`.swap-napcat-full.cmd`，失败自动回滚）：

```
旧目录改名 napcat.bak-4181 → 新目录整个铺上去 → config/ 和 plugins/ 从备份盖回来
登录态在 QQ 自己的数据目录里，换壳不用重新扫码
```

**验证**：

```bash
qce poke user:1473517806                    # 私聊戳
qce poke group:913807639 1473517806         # 群里戳
```

**顺带发现（体检脚本的两个假警报）**：

1. `get_group_msg_history` 的 `count` 太小会返回**空数组**，不是"没消息"。
   实测 `1`、`2` 都是空，`5` 才有内容 → 体检固定用 `count: 10`。
   这一条让体检在明明有消息时报「群消息为空」，看着像读接口瘫了。
2. 「监视器日志 N 秒前」写死了 `output/qq-watch.log`，但实际在跑的是
   `qq-watch-v2.log`，拿旧日志算年龄会误报 → 改成取两份里更新的那份。

### 7.1 收戳一戳：走 WebSocket 事件流，不是靠轮询

**能不能收到别人戳我，跟能不能戳别人是两件事。** 戳出去是 HTTP 调用，
收回来靠事件推送。NapCat 的 `onebot11_<uin>.json` 里 `httpServers[0].enableWebsocket: true`，
所以 **同一个 3000 端口也能当 WS 连**：

```
ws://127.0.0.1:3000/?access_token=<token>
```

`scripts/qq-poke-watch.mjs` 就是常驻监听它，收到 `notice/notify/poke` 后
走跟 qq-watch 同一条投递通道写进会话（`--pvp` 会自动戳回去，90s 冷却）。

**字段语义两种不统一，别凭直觉写**（实测原始事件）：

| 场景 | `user_id` | `target_id` | `sender_id` |
|---|---|---|---|
| 群戳 | 发起者 | 被戳的 | 无 |
| 私戳 | 被戳的那一方 | 同 `user_id` | 发起者 |

所以「是不是戳我」判定也不同：群看 `target_id === 我`，私聊看 `user_id === 我`。
混用会把"我戳别人"误报成"别人戳我"——我第一次就写错了。

**`raw_info` 里有文案**：`[{type:'nor', txt:'戳了戳'}, …]` 或
`[..., {txt:'拍了拍'}, ..., {txt:'的八块肚腩'}]`。拼起来就是这记戳的完整话术，
通知里带上它比干巴巴一句"戳了你"有意思。

**验证办法**：`node scripts/poke-probe.mjs 20` 连 20 秒，期间自己戳一下对方，
能打 `notice/notify/poke` 就说明事件链路通。
